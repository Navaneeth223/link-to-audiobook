# Audiobook export: feasibility and constraints

## Current feasibility

Audiobook export is **not implemented** in this repository. The current `SpeechProvider` in `src/core/speech.ts` exposes volume control only; the only provider is `BrowserSpeechProvider`, which submits text to the browser/OS `SpeechSynthesis` service. That API does not expose the synthesized audio samples, so its output cannot be captured or exported. Recording system audio or attempting to work around this limitation is not supported.

There is no in-browser neural TTS provider, Voice Studio, generated-audio cache, worker-based exporter, or export storage in the current build. The application presently keeps an opened story in memory and does not persist its text. Consequently:

- Browser speech must have audiobook download disabled, with an explanation that it cannot provide audio samples.
- A “Switch to a downloadable voice” action can only be offered after a sample-producing provider is implemented and an eligible voice is actually available. This build cannot truthfully offer that switch yet.
- A provider is export-eligible only if it returns audio samples locally in the browser. A future optional bring-your-own-key provider would need a separate privacy disclosure because sending text to that provider would violate this project's no-upload export requirement; it is therefore out of scope for a privacy-preserving export.
- Voice Studio export must be gated on a verifiable, user-owned consent record. Neither Voice Studio nor that record exists in this build.

The intended processing boundary is document text → existing chapter/paragraph/sentence structure → local sample-producing provider in a Web Worker → chunk-wise local encoding and storage → user-initiated save. Text and audio must not be sent to the reader API or another network service. Browser speech is not a substitute for this pipeline.

## Output-format decision

When a local audio-sample provider and a tested encoder are available, the preferred default is **one MP3 per selected chapter, packaged as a ZIP**. This preserves chapter boundaries, permits per-chapter processing and retry, and avoids assembling the entire book's encoded audio in memory. MP3 is broadly playable, and ZIP is a familiar container for multiple chapter files. The encoder and ZIP implementation must be reviewed for compatible licenses before they are added; no encoder has yet been selected or added.

**WAV** is a useful lossless, simple-to-validate alternative, but its size makes it unsuitable as the default for long books. A 24 kHz, 16-bit, mono PCM WAV is approximately 172.8 MB (about 164.8 MiB) per hour, before small container overhead. WAV should require an explicit size warning and should be written incrementally when the browser supports it.

A **single MP3 with ID3v2 CHAP/CTOC frames** could produce one broadly playable file with chapter navigation, but requires verified muxing, metadata, and compatibility tests. It is not the initial default and must not be presented as available until those tests pass.

**M4B/AAC** is deferred. Feature detection for `AudioEncoder` alone is not sufficient evidence that a reliable, chapter-marked M4B can be produced across target browsers. Do not show this option unless end-to-end encoding and chapter metadata have been validated on the actual supported implementations.

All exported files should include the requested title, author, voice name, and “Generated by Private Story Reader” metadata where the selected container supports them. Metadata must not contain story text. Chapter filenames must be sanitized.

## Size and generation estimates

Estimates should be calculated from selected chapter text and the chosen output settings, then refined using a short on-device synthesis benchmark. Do not claim a fixed generation speed: time depends on the voice/model, text, browser, device, thermal state, and available acceleration.

For speech duration `D` seconds and MP3 bitrate `B` kilobits/second, the approximate audio payload is `D × B / 8,000` megabytes in decimal units, plus small container/ZIP overhead. At 64, 96, and 128 kbps mono, one hour is approximately 28.8, 43.2, and 57.6 MB respectively. Speech time may be estimated from text only as a rough initial estimate; the benchmark should estimate this device's synthesis real-time factor and visibly label the result approximate.

Expected generation rate is reported as a measured, per-device estimate, not a promise. WebGPU may improve neural synthesis when a compatible model, browser, and GPU path exist; WASM/CPU synthesis is generally more constrained. This repository currently includes neither implementation, and no speed has been measured for it. An estimate should be refreshed from the initial chunk(s) and updated as the export progresses.

## Browser and storage support

| Browser family | Local Web Workers / browser speech | Direct save path | Export considerations |
|---|---|---|---|
| Chromium desktop (Chrome/Edge) | Available in current releases; speech voices remain OS/browser-dependent | File System Access API is available in supported secure contexts | Preferred path for incremental writes. Neural WebGPU/model support still depends on device and must be detected. |
| Firefox desktop | Web Workers and browser speech are available | `showSaveFilePicker` is not generally available | Use a tested OPFS/IndexedDB fallback; assembling a large final Blob can exceed practical memory. Prefer chapter exports. |
| Safari on macOS | Web Workers and browser speech are available | File System Access API is not generally available | Use a tested OPFS/IndexedDB fallback; confirm quota and codec behavior at runtime. |
| Safari on iPhone/iPad | Web Workers and browser speech are available, with platform restrictions | No generally available `showSaveFilePicker` path | Tight memory, storage, background-tab, and download constraints make long, whole-book exports unreliable. Prefer one chapter at a time; keep the tab open. |
| Chromium on Android | Web Workers and browser speech are available | File System Access API availability varies by browser/version/device | Detect the save and storage APIs at runtime; mobile memory and background throttling still constrain large exports. |

This is a capability overview, not a guarantee for every browser version or device. The implementation must feature-detect APIs and handle unavailable storage, quota failures, interrupted tabs, and denied file-picker requests. It must not infer available disk space from a quota estimate or claim an export was saved when the write was not confirmed.

There is no universal browser memory limit or reliable cross-browser way to reserve the memory required for a large Blob. Never retain the whole book's PCM or encoded output in memory. Write chunks incrementally to a user-selected file where supported, or to origin-private local storage for resumable work. A final ZIP/Blob fallback still has to assemble a download and can require substantial memory; warn before large exports and recommend per-chapter output. Apply configurable duration and storage safeguards, and report quota/write errors in plain language.

## Privacy, retention, and user expectations

Any future export storage must be local to the browser origin, contain only the minimum resumable encoded chunks and manifest, and be removed after successful completion, cancellation, or the corresponding clear-data action. If resumability across reloads is supported, tell the user what remains and provide an explicit delete action. Do not log story text, persist it in an export manifest, or send story text/audio in requests.

The export UI must state: “For personal listening. You are responsible for having the right to convert this document. Do not redistribute content you don't own.” A required acknowledgement is appropriate before generation. Voice Studio audio may only be exported under the user's own valid consent record; export responsibility and rights remain with the user. Do not add sharing or publishing features.

## Readiness checklist

Before enabling export, implement and test a local sample-producing voice provider, a worker-safe chunk pipeline, a compatible encoder, bounded local storage with cleanup and resumability, and the user-facing eligibility/rights/privacy states. Validate real generated files, chapter metadata, interruption/recovery, storage-full behavior, and no network transmission of text or audio. Until then, the browser-voice explanation is the only honest user experience.
